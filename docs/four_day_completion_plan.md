# 4-დღიანი დასრულების გეგმა

მიზანი: პროექტი უნდა მივიდეს მუშა დემო ვერსიამდე, რომელიც აკმაყოფილებს შეფასების მთავარ კრიტერიუმებს: ფუნქციონალობა, კოდის ხარისხი, დოკუმენტაცია, პრეზენტაცია და პრობლემის დასაბუთებული გადაწყვეტა.

## დღე 1 - Backend

მთავარი ამოცანები:

- FastAPI პროექტის დამატება. - შესრულებულია
- მოდელის ჩატვირთვის ლოგიკის გამოტანა API სერვისში. - შესრულებულია
- endpoint-ების შექმნა: - შესრულებულია
  - `GET /health`
  - `GET /features`
  - `POST /predict`
- error handling-ის დამატება არასწორი input-ისთვის. - შესრულებულია
- Swagger დოკუმენტაციის შემოწმება. - მზად არის `/docs` მისამართზე

მოსალოდნელი შედეგი:

- backend მუშაობს ლოკალურად და აბრუნებს პროგნოზს JSON ფორმატში.

## დღე 2 - Frontend

მთავარი ამოცანები:

- React აპლიკაციის შექმნა. - შესრულებულია
- პაციენტის მონაცემების ფორმის დამატება. - შესრულებულია sample patient-ის ბაზაზე
- API-სთან დაკავშირება. - შესრულებულია
- შედეგის ჩვენება: - შესრულებულია
  - risk probability
  - risk level
  - predicted class
  - top SHAP factors
- UI-ის გამარტივება ისე, რომ დემოს დროს გასაგები იყოს. - შესრულებულია

მოსალოდნელი შედეგი:

- მომხმარებელს შეუძლია ვებ-ინტერფეისიდან მიიღოს პროგნოზი.

## დღე 3 - დოკუმენტაცია და ტესტირება

მთავარი ამოცანები:

- README-ის დასრულება.
- API დოკუმენტაციის აღწერა.
- არქიტექტურის მოკლე აღწერა.
- ინსტალაციის ნაბიჯების ჩამოწერა.
- შეზღუდვების და ეთიკური მხარის აღწერა.
- რამდენიმე ხელით ტესტის ჩატარება backend-ზე და frontend-ზე.

მოსალოდნელი შედეგი:

- პროექტი დოკუმენტირებულია და შესაძლებელია მისი ლოკალურად გაშვება ინსტრუქციების მიხედვით.

## დღე 4 - პრეზენტაცია და დემო

მთავარი ამოცანები:

- 20-25 წუთიანი პრეზენტაციის სტრუქტურის მომზადება.
- დემოს სცენარის მომზადება.
- სლაიდებში ჩასასმელი ძირითადი პუნქტების განსაზღვრა:
  - პრობლემა
  - მონაცემები
  - preprocessing
  - მოდელები და შედეგები
  - XAI/SHAP
  - სისტემა და demo
  - შეზღუდვები
  - მომავალი განვითარება
- შესაძლო კითხვებზე პასუხების მომზადება.

მოსალოდნელი შედეგი:

- პროექტი მზად არის კომისიის წინაშე საჩვენებლად.

## რისკები

- frontend-ზე დროის დაკარგვა არ ღირს, თუ backend ჯერ არ არის სტაბილური.
- თუ დრო არ ეყოფა სრულ UI-ს, მინიმალური ინტერფეისი და Swagger demo სჯობს არასტაბილურ დიდ frontend-ს.
- პრეზენტაციაში აუცილებლად უნდა ითქვას, რომ სისტემა არის risk prediction prototype და არა დამოუკიდებელი დიაგნოსტიკური სისტემა.
