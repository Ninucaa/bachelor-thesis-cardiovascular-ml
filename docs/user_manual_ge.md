# მომხმარებლის სახელმძღვანელო

პროექტი: გულ-სისხლძარღვთა სავარაუდო დიაგნოზის პროგნოზირების decision-support სისტემა

ეს სახელმძღვანელო აღწერს, როგორ გამოიყენოს მომხმარებელმა ვებაპლიკაცია demo რეჟიმში და როგორ წაიკითხოს მიღებული შედეგი. სისტემა არ სვამს საბოლოო სამედიცინო დიაგნოზს. იგი აჩვენებს, რომელ ICD-კოდირებულ გულ-სისხლძარღვთა დიაგნოზის ჯგუფთან ხედავს მოდელი ყველაზე ძლიერ სიგნალს.

## 2. პაციენტის მონაცემების შევსება

აპლიკაციის მარცხენა მხარეს ჩანს პაციენტის მონაცემები. Demo რეჟიმში თავდაპირველად იტვირთება ერთი test-split პაციენტი. მომხმარებელს შეუძლია შეცვალოს მხოლოდ გასაგები კლინიკური ველები, ხოლო backend-ში იგზავნება სრული model-ready feature payload.

ძირითადი ველები:

- ასაკი და სქესი
- წონა კილოგრამებში და სიმაღლე სანტიმეტრებში
- BMI, რომელიც ითვლება ავტომატურად
- ამბულატორიული და გადაუდებელი განყოფილების არტერიული წნევა
- სამედიცინო ისტორია: დიაბეტი, თირკმლის ქრონიკული დაავადება, სიმსუქნე, თამბაქო/ნიკოტინი
- ლაბორატორიული მაჩვენებლები: კრეატინინი, ჰემოგლობინი, გლუკოზა, NT-proBNP, Troponin T, ქოლესტერინი და სხვა
- triage მაჩვენებლები: გულისცემა, სუნთქვის სიხშირე, SpO2, ტემპერატურა, სიმძიმე
- ECG პასუხი / ელექტროკარდიოგრამის მოკლე შეფასება
- დამატებითი სიმპტომების ტექსტური ველი

## 3. დამატებითი სიმპტომების ველი

დამატებითი სიმპტომების ველში მომხმარებელს შეუძლია ჩაწეროს თავისუფალი ტექსტი, მაგალითად:

```text
პაციენტს აქვს გულმკერდის ტკივილი, ქოშინი და გულის ფრიალი.
```

სისტემა ცდილობს გაარჩიოს:

- ამჟამად არსებული სიმპტომი (`აღინიშნება`)
- უარყოფილი სიმპტომი (`უარყოფს`)
- წარსულში არსებული სიმპტომი (`ანამნეზში`)
- გაურკვეველი ან დასაზუსტებელი სიმპტომი (`დასაზუსტებელია`)

მოდელში დადებით ნიშნად გადადის მხოლოდ ის სიმპტომი, რომელიც ტექსტში ამჟამინდელ ჩივილად არის აღწერილი. მაგალითად, „გულმკერდის ტკივილს უარყოფს“ არ უნდა ჩაითვალოს დადებით სიმპტომად.

Parser ამოიცნობს როგორც პირდაპირ ფორმებს, ასევე ხშირ ქართულ სინონიმებს, მაგალითად: „მკერდში მოჭერა“, „გულზე აწვება“, „სუნთქვა უჭირს“, „ჰაერი არ ყოფნის“, „გული უჩქარდება“, „გონება დაკარგა“, „ფეხები უსივდება“. დამატებით ტექსტურ კონტექსტად ჩანს მაღალი/დაბალი წნევა და თავის ტკივილი. ეს დამატებითი ტექსტური ნიშნები clinical report-ში ჩანს, მაგრამ model probability-ს პირდაპირ არ ცვლის.

## 4. ECG პასუხი

ECG ველი არასავალდებულოა. მომხმარებელს შეუძლია მიუთითოს მოკლე შეფასება, მაგალითად:

- არ არის ხელმისაწვდომი
- ნორმალური ECG
- ST elevation / მწვავე ინფარქტის ეჭვი
- ST depression / იშემიის ეჭვი
- არითმიის ნიშნები
- წინაგულთა ფიბრილაციის ნიშნები
- QRS გაფართოება
- QT გახანგრძლივება
- სხვა პათოლოგიური ცვლილება

მნიშვნელოვანია: ECG ველი ამ ვერსიაში არ ცვლის მოდელის probability-ს, რადგან time-aware მოდელი ECG-derived feature-ებზე ხელახლა არ არის გაწვრთნილი. ECG გამოიყენება როგორც დამატებითი კლინიკური კონტექსტი პაციენტის ანგარიშსა და ექიმისთვის გადასამოწმებელ პუნქტებში.

## 5. ლაბორატორიული ნორმები და BMI

ლაბორატორიული მაჩვენებლებისა და BMI-ის ნორმების ნახვა შესაძლებელია ცალკე ფანჯარაში. ეს ნაწილი ეხმარება მომხმარებელს შეაფასოს, კონკრეტული მნიშვნელობა ნორმის ფარგლებშია თუ არა.

მაგალითად:

- BMI 18.5-24.9 მიიჩნევა ნორმის ფარგლებში.
- გლუკოზა, კრეატინინი, NT-proBNP და Troponin T გამოიყენება როგორც კლინიკური კონტექსტის ნაწილი.

## 6. პროგნოზის გაშვება

პროგნოზის მისაღებად მომხმარებელი აჭერს ღილაკს:

```text
პროგნოზის გაშვება
```

Frontend აგზავნის მონაცემებს `POST /predict` endpoint-ზე. Backend ამოწმებს feature schema-ს, ტვირთავს შესაბამის XGBoost მოდელებს და აბრუნებს პროგნოზს.

თუ ფორმაში მითითებულია საეჭვო ან უკიდურესი მნიშვნელობა, მაგალითად ძალიან მაღალი Troponin T, ძალიან დაბალი SpO2, უკიდურესი წნევა ან ტემპერატურა, აპლიკაცია აჩვენებს input warning-ს. Warning პროგნოზს ავტომატურად არ ბლოკავს, მაგრამ მომხმარებელს სთხოვს მნიშვნელობის და ერთეულის გადამოწმებას.

ტემპერატურის ველი Celsius-შია. თუ მომხმარებელი შემთხვევით Fahrenheit მნიშვნელობას შეიყვანს, მაგალითად 98.6, სისტემა მას ავტომატურად Celsius-ში გადაიყვანს და status bar-ში მიუთითებს გარდაქმნილ მნიშვნელობას.

- პაციენტის მოკლე პროფილს
- სავარაუდო მთავარ მიმართულებას

## 10. მოდელის ტექნიკური შეფასება

ტექნიკური შეფასების ფანჯარა განკუთვნილია უფრო ტექნიკური მომხმარებლისთვის ან კომისიისთვის. იქ ჩანს AUC, Recall და Precision ძირითადი და subtype მოდელებისთვის.

მარტივი ინტერპრეტაცია:

- AUC აჩვენებს, რამდენად კარგად არჩევს მოდელი შესაბამის და არაშესაბამის შემთხვევებს.
- Recall აჩვენებს, რამდენ დაავადებულ შემთხვევას პოულობს მოდელი.
- Precision აჩვენებს, დადებითი პასუხებიდან რამდენია უფრო სარწმუნო.

## 11. Use Cases

Use case 1 - demo პაციენტის შეფასება:

1. მომხმარებელი ხსნის frontend-ს.
2. იტვირთება sample patient.
3. მომხმარებელი აჭერს პროგნოზის ღილაკს.
4. სისტემა აჩვენებს სავარაუდო დიაგნოზის ჯგუფს და განმსაზღვრელ ფაქტორებს.

Use case 2 - შეცვლილი მონაცემებით პროგნოზი:

1. მომხმარებელი ცვლის ასაკს, წონას, სიმაღლეს, წნევას ან ლაბორატორიულ პასუხებს.
2. BMI ავტომატურად ახლდება.
3. მომხმარებელი ხელახლა უშვებს პროგნოზს.
4. სისტემა აბრუნებს განახლებულ დიაგნოსტიკურ მიმართულებას.

Use case 3 - სიმპტომების ტექსტური ანალიზი:

1. მომხმარებელი დამატებით სიმპტომებში წერს პაციენტის ჩივილებს.
2. სისტემა გამოყოფს ამოცნობილ სიმპტომებს.
3. პროგნოზისას დადებითი ამჟამინდელი სიმპტომები შედის model payload-ში.

Use case 4 - საეჭვო input-ის გადამოწმება:

1. მომხმარებელი შეიყვანს უკიდურეს მნიშვნელობას, მაგალითად SpO2 82% ან ტემპერატურა 98.6.
2. სისტემა აჩვენებს warning-ს ან ერთეულის გარდაქმნის შეტყობინებას.
3. მომხმარებელი გადაამოწმებს მნიშვნელობას და საჭიროების შემთხვევაში ასწორებს.
4. პროგნოზი მაინც შეიძლება გაეშვას, მაგრამ დასკვნა უნდა შეფასდეს warning-ის გათვალისწინებით.
