# პროგრესის ჟურნალი

შენიშვნა: ეს ჟურნალი არის პროექტის სამუშაოს რეკონსტრუირებული და დალაგებული აღწერა. იგი არ უნდა იყოს წარმოდგენილი როგორც ზუსტად ყოველ კვირაში შევსებული დღიური, თუ რეალურად ასე არ წარმოებულა. სწორი ფორმულირებაა: “ქვემოთ მოცემულია პროექტის შესრულებული სამუშაოს ეტაპობრივი შეჯამება და დარჩენილი სამუშაოს გეგმა”.

## ეტაპი 1 - თემის განსაზღვრა და პრობლემის ფორმულირება

შესრულებული სამუშაო:

- განისაზღვრა პროექტის თემა: გულ-სისხლძარღვთა დაავადებების რისკის პროგნოზირება მანქანური სწავლების მეთოდებით.
- ჩამოყალიბდა ძირითადი პრობლემა: კლინიკურ გარემოში ექიმს უწევს მრავალი პარამეტრის ერთდროული ანალიზი, რაც ზრდის შეცდომის ან დაგვიანებული შეფასების რისკს.
- განისაზღვრა პროექტის მიზანი: შეიქმნას გადაწყვეტილების მიღების მხარდამჭერი პროტოტიპი, რომელიც პაციენტის მონაცემებიდან დაადგენს რისკის ალბათობას.

მიღებული შედეგი:

- ჩამოყალიბდა პროექტის მთავარი იდეა, მიზანი და მოსალოდნელი შედეგები.

## ეტაპი 2 - მონაცემთა ბაზის მომზადება

შესრულებული სამუშაო:

- გამოყენებული იქნა უკვე აწყობილი მონაცემთა ფაილი `cardio_training_features.csv`.
- შემოწმდა მონაცემთა ზომა, სვეტები, target ცვლადი და train/validation/test დაყოფა.
- დადასტურდა, რომ train, validation და test ნაწილებს შორის ერთი და იგივე პაციენტი არ მეორდება.
- შემოწმდა გამოტოვებული მნიშვნელობები, დუბლიკატები და ექსტრემალური მნიშვნელობები.

მიღებული შედეგი:

- მონაცემთა საწყისი ფორმა: `546,028` ჩანაწერი და `76` სვეტი.
- target ცვლადი: `target_cvd`.
- დუბლიკატი ჩანაწერები არ აღმოჩნდა.
- პაციენტების გაჟონვა train/validation/test ნაწილებს შორის არ აღმოჩნდა.

## ეტაპი 3 - მონაცემთა გასუფთავება

შესრულებული სამუშაო:

- შეიქმნა მონაცემთა წინასწარი დამუშავების სკრიპტი.
- მოდელიდან ამოღებულია იდენტიფიკატორები: `subject_id`, `hadm_id`.
- ამოღებულია სრულიად უსარგებლო ან მუდმივი სვეტები: `lab_troponin_i_mean`, `lab_troponin_i_count`.
- `ecg_available` ცვლადის გამოტოვებული მნიშვნელობები გადაიქცა `0`-ად.
- არარეალისტური კლინიკური მნიშვნელობები ჩანაცვლდა გამოტოვებულ მნიშვნელობად.
- დაემატა missing indicator სვეტები, რათა მოდელმა იცოდეს რომელი მონაცემი იყო თავდაპირველად გამოტოვებული.
- გამოტოვებული რიცხვითი მნიშვნელობები შეივსო მხოლოდ train ნაწილის მედიანებით.

მიღებული შედეგი:

- მომზადდა ფაილი `data/processed/cardio_model_ready.csv`.
- საბოლოო მონაცემებში გამოტოვებული მნიშვნელობები აღარ არის.
- მოდელისთვის ხელმისაწვდომია `137` feature.

## ეტაპი 4 - მოდელების გაწვრთნა და შედარება

შესრულებული სამუშაო:

- შეიქმნა `src/train_model.py`.
- გაიწვრთნა სამი მოდელი:
  - Logistic Regression
  - Random Forest
  - XGBoost
- შეფასდა მოდელები validation და test მონაცემებზე.
- გამოყენებული მეტრიკები:
  - AUC-ROC
  - F1-score
  - Recall/Sensitivity
  - Precision
  - Confusion Matrix

მიღებული შედეგი:

- საუკეთესო მოდელი გახდა XGBoost.
- test შედეგები:
  - AUC-ROC: `0.8754`
  - F1-score: `0.8536`
  - Recall/Sensitivity: `0.8818`
  - Precision: `0.8271`

## ეტაპი 5 - პროგნოზის სკრიპტი და ახსნადობა

შესრულებული სამუშაო:

- შეიქმნა `src/predict.py`.
- სკრიპტი ტვირთავს გაწვრთნილ XGBoost მოდელს.
- შესაძლებელია ერთი პაციენტის რისკის პროგნოზირება.
- დაემატა SHAP ახსნადობა, რომელიც აჩვენებს ტოპ ფაქტორებს, რომლებმაც პროგნოზზე გავლენა მოახდინა.

მიღებული შედეგი:

- სისტემას შეუძლია დააბრუნოს რისკის ალბათობა, პროგნოზირებული კლასი, რისკის დონე და მნიშვნელოვანი ფაქტორები.

## ეტაპი 6 - FastAPI backend

შესრულებული სამუშაო:

- შეიქმნა FastAPI backend.
- მოდელის ჩატვირთვის და პროგნოზის ლოგიკა გამოიყო `src/api/model_service.py` ფაილში.
- შეიქმნა API schema-ები `src/api/schemas.py` ფაილში.
- დაემატა endpoint-ები:
  - `GET /health`
  - `GET /features`
  - `POST /predict`
- დაემატა validation არასწორი feature payload-ისთვის.
- შემოწმდა რეალური მოთხოვნები ლოკალურ სერვერზე.

მიღებული შედეგი:

- backend აბრუნებს მოდელის სტატუსს, feature-ების სიას და პროგნოზს SHAP ახსნით.
- არასრული feature payload-ის შემთხვევაში API აბრუნებს `422` შეცდომას missing feature-ების დეტალებით.

## ეტაპი 7 - React frontend

შესრულებული სამუშაო:

- შეიქმნა React/Vite frontend.
- frontend უკავშირდება FastAPI backend-ს.
- დაემატა sample patient-ის ჩატვირთვა `GET /sample-patient` endpoint-იდან.
- მომხმარებელს შეუძლია შეცვალოს რამდენიმე ძირითადი კლინიკური ველი:
  - ასაკი
  - სქესი
  - creatinine
  - hemoglobin
  - glucose
  - ED heart rate
  - systolic/diastolic BP
  - ECG availability
  - ICU vital count
- frontend აგზავნის სრულ feature payload-ს `POST /predict` endpoint-ზე.
- შედეგის გვერდზე ჩანს risk probability, risk level, predicted class და SHAP ფაქტორები.

მიღებული შედეგი:

- შექმნილია მუშა demo ინტერფეისი, რომელიც გამოდგება დაცვის დროს სისტემის ძირითადი ფუნქციონალის საჩვენებლად.

## დარჩენილი სამუშაო

- არქიტექტურის, API-ის და გამოყენების დოკუმენტაციის მომზადება.
- პრეზენტაციისა და დემოს მომზადება.
